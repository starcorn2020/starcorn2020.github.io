position

How I use AI

I don't treat AI as a code-generation shortcut. I run agents inside a structured engineering workflow and work primarily as the architect and system designer. Agent output is a proposal: it has to be grounded, constrained and verified before it becomes part of a system.

The agent does

I stay responsible for

  • Architecture

AI is not an authority in this workflow. It is an engineering worker whose output is reviewed like any other contribution.

process

End-to-end engineering workflow

The same sequence runs from a first feasibility read through to what gets written back into long-term memory. Each stage has an output someone else could check.

  1. 01

    Project evaluation

    Scope, feasibility, and whether the problem is worth solving in the shape it arrived in.

  2. 02

    Evidence collection

    Inspect the repository, documentation, schemas, interfaces and runtime state before deciding anything.

  3. 03

    Architecture and constraints

    Boundaries, invariants, latency budget and failure behaviour — defined by me, stated explicitly to the agent.

  4. 04

    Implementation planning

    Decomposition into tasks small enough to review and verify one at a time.

  5. 05

    AI-assisted development

    Code generation, refactoring and test drafting, bounded by the constraints set in stage three.

  6. 06

    Executable verification

    Compiler, test suites, integration and black-box runs, benchmarks, runtime observation, diff review.

  7. 07

    Post-implementation review

    Compare the result against the acceptance criteria — not against the agent's own summary of its work.

  8. 08

    Persistent knowledge update

    Verified conclusions, and only verified conclusions, are written back into long-term project memory.

reliability

Three-layer hallucination control

This does not eliminate hallucination. It is designed to reduce the risk and to make unsupported claims easy to detect — early, and by something other than the model.

01

Evidence-driven instruction

Inspect before acting. Evidence before assumptions.

Before implementation, the agent is instructed to inspect the real environment — code, documentation, interfaces, schemas, runtime state, data — and to bring back what it found. The instruction framework matters; the product name behind it does not. Model knowledge is never allowed to stand in as project truth.

02

Explicit source of truth

Unknown is a valid state.

Execution defines which sources are authoritative: repository code, architecture documents, API schemas, specifications, tests, runtime behaviour, real datasets, verified engineering decisions. Every statement carries a state, so a missing fact never quietly becomes an invented assumption.

  • CONFIRMED
  • INFERRED
  • PENDING
  • SPEC GAP
  • UNKNOWN

03

Executable verification

A claim is not proof. An execution result is evidence.

An agent saying that something works proves nothing. Authority belongs to executable systems and observable results, not to the model's explanation of its own output.

  • cargo check
  • cargo test
  • integration tests
  • white-box tests
  • black-box tests
  • benchmarks
  • runtime observation
  • real queries, real output
  • git diff

context

Persistent semantic memory

Long projects run across many sessions and many agent contexts. I keep engineering knowledge in a document-backed external memory and retrieve it semantically, instead of reloading an entire knowledge base into every session.

What the memory holds

  • Notion workspace and structured Markdown
  • Project and architecture documentation
  • Decision records
  • Research and implementation notes
  • Verified findings

What vector search does, and doesn't

Vector similarity does not guarantee correctness. It improves retrieval relevance and context precision: the agent sees the most semantically relevant documents instead of an indiscriminate dump of the whole knowledge base.

It reduces:

  • Irrelevant context
  • Context dilution
  • Cross-session knowledge loss
  • Repeated rediscovery of the same facts

The write-back gate

Only verified conclusions are promoted into persistent memory. This is what keeps a hallucination from being stored once and then retrieved as established fact by every session after it.

Market Data Service

Rust market-data middleware. Take-home engineering assignment from a leading trading firm.

Repository

Background

The upstream emits a continuous stream of BookMessage order-book updates across many instruments. The service has to maintain the latest snapshot per instrument, serve request/response snapshot access, publish real-time updates to many subscribers, isolate slow consumers, and keep slow or disconnected clients away from the ingest hot path — for local and remote clients alike. Transport, fan-out behaviour, snapshot representation and wire subscription semantics were deliberately left open as engineering design decisions.

Key decisions

Non-blocking ingest
The hot path never waits on subscribers. Fan-out is non-blocking, so a slow consumer cannot back-pressure ingest.
Subscriber isolation
Each subscriber gets an independent bounded queue. When a queue fills, messages are dropped for that subscriber alone, and a cumulative dropped-message count makes the loss observable rather than silent.
Clear abstraction boundary
The upstream simulator sits behind an Upstream trait, so the real production feed can replace it without changing the rest of the service.
Transport
gRPC over HTTP/2 for cross-host clients: request/response for snapshots, server streaming for subscriptions.

Trade-off philosophy

The design deliberately favours predictability, failure isolation, correctness and operational safety, while keeping the hot path low-latency and non-blocking.

In the interview discussion, the interviewer described the design as "the safest" among the submissions. I read that as the result of a deliberate trade-off rather than a verdict on which submission was best: a conservative architecture balancing low latency against subscriber isolation, explicit failure behaviour and operational safety.

My role

System design, constraints, latency and failure requirements, and every trade-off decision.

The agent's role

Interpreting the assignment, exploring architectures, laying out trade-offs, implementation planning, Rust code generation, test planning, review support, verification runs.

  • tonic gRPC
  • Tokio
  • DashMap
  • bounded queues
  • deterministic integration tests

EdgeX Singer

A Rust-side Stark signing compatibility layer, built for an EdgeX exchange integration.

Repository

Background

While building an EdgeX exchange integration at Binquant, the exchange required Stark-based cryptographic signing. The Rust StarkNet-related libraries available at the time did not produce signatures compatible with the exchange's required authentication flow. With AI assistance I investigated the signing algorithm and implemented the Rust-side cryptographic logic the integration needed.

Engineering problem

Reproducing the signing pipeline end to end: StarkCurve elliptic-curve operations, Pedersen hashing, order hash construction, deterministic signing, L2 order fields, fee calculation and key derivation — each step matching the exchange byte for byte, because a signature is either accepted or it is not.

Outcome

A working Rust implementation that produces signatures the exchange accepts, integrated into the trading-system's exchange connectivity workflow.

This is an implementation and compatibility solution. StarkCurve, Pedersen hashing and the StarkNet signing scheme are existing designs; the work here is reproducing them correctly in Rust.

Implemented components

  • ec_add
  • ec_double
  • mod_inverse
  • Pedersen hash
  • limit-order hash
  • StarkNet-style signing
  • L2 order-field construction
  • private-key derivation

The agent's role

Investigating specifications, comparing implementations, translating algorithm concepts into Rust, debugging incompatibilities, generating implementation scaffolding, validating intermediate calculations against known values.

My role

Defining the correctness requirements, verifying compatibility against the exchange, reviewing the cryptographic behaviour, and integrating the result into the trading system.

Stack

  • Rust
  • num-bigint
  • starknet-crypto
  • serde
  • rust_decimal
